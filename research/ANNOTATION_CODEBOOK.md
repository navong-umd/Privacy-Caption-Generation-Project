# Annotation Codebook (Gate G1)

How two annotators label PRCS flows on the PAcT taxonomy, and how those labels become the locked human test set. Label definitions follow Jain et al., *PAcT* (WiSec 2022).

## 1. What you are labeling

Each row is one **flow**: personal data read by a *source* API and reaching a *sink* API, inside one app. You see:

| Column | Meaning |
|---|---|
| `app_package` | The app. |
| `class_name`, `method_name` | Where the flow starts. |
| `source_api` | The call that reads personal data (e.g. `LocationManager->getLastKnownLocation`). |
| `pi_type` | The kind of personal data, from the knowledge base. |
| `sink_api`, `sink_type` | Where the data goes: `network`, `storage`, `logging`, `ipc`, `serialization`, or `heuristic_unknown`. |
| `snippet` | The start of the decompiled code (Dalvik, one statement per line). |

You never see the weak heuristic labels. Judge from the evidence in the row.

## 2. Labels

Mark `1` in every column that applies. Both heads are multi-label; most flows have at least one Practice and one Purpose.

**Practice: what the app does with the data**

| Column | Mark it when |
|---|---|
| `P_Processing` | The data is used inside the app: transformed, compared, displayed, combined with other data. |
| `P_Collecting` | The app reads or gathers the data (the source call itself usually justifies this). |
| `P_Sharing` | The data leaves the app: sent to a server, a third-party SDK, another app or component. A `network` or `ipc` sink is strong evidence. Writing to local storage or a log alone is not sharing. |
| `P_Other` | A practice that is none of the above. Use rarely and say why in `notes`. |

**Purpose: why**

| Column | Mark it when |
|---|---|
| `U_Functionality` | The flow serves a feature the user asked for (maps, login, messaging, settings). |
| `U_Advertisement` | The flow serves ads or ad targeting: the sink belongs to an ad SDK or ad endpoint. |
| `U_Analytics` | The flow serves usage measurement: crash reporting, telemetry, analytics SDKs. |
| `U_Other` | A purpose that is none of the above. Explain in `notes`. |

**Decision rules**

1. Label what the evidence shows, not what the app probably does elsewhere.
2. If the sink belongs to a third-party SDK, the SDK's role decides the purpose (an analytics SDK is `U_Analytics` even inside a feature screen).
3. A flow can serve two purposes (a location sent to both a maps tile server and an analytics SDK). Mark both.
4. If the sink is `heuristic_unknown` and the code does not make the destination clear, mark only what you can support and set `confidence` to 1.
5. If the source does not actually read personal data (a false positive from the analysis), mark `P_Other` + `U_Other` and write `not personal data` in `notes`.

## 3. Confidence and notes

- `confidence`: `3` sure, `2` probably, `1` unsure. Blank counts as `3`.
- `notes`: anything that would help adjudication, especially for `Other`, rule 4 and rule 5 cases.
- `annotator` is pre-filled on your sheets. Do not change it.

## 4. The kit and the order of work

Generated by `python -m step2_dataset.make_annotation_sheet --dataset <dataset> --kit <kit dir>`:

| Sheet | Who | Rows | Used for |
|---|---|---|---|
| `calibration_<you>.csv` | both, separately | 20 (validation split) | Practice and codebook refinement only. Never trained on or reported. |
| `overlap_<you>.csv` | both, separately | 100 (test split) | Agreement (Cohen's kappa), then adjudicated into the test set. |
| `solo_<you>.csv` | one each | 150 each (test split) | The rest of the 400-flow test set. |

`manifest.json` records the seed and every sheet's ids; `test_ids` (overlap + both solo sets) is the test split.

1. **Calibration.** Label your calibration sheet alone, then meet. Run agreement on it (output to a scratch path, not `experiments/`), discuss each disagreement, and add worked examples to section 5. Repeat with a fresh 20-flow calibration draw if macro kappa over defined labels is below 0.6 or fewer than 6 of the 8 labels are defined.
2. **Overlap.** Label your overlap sheet without discussing it.
3. **Solo.** Label your solo sheet.
4. **Adjudication.** Ali resolves every overlap disagreement in the adjudication sheet (both earlier answers are shown in the `a_*` / `b_*` columns).

## 6. Commands

```bash
K=data/annotation_kit
D=data/corpus_run/dataset

# ingest each filled sheet (annotator comes from the sheet)
python -m step2_dataset.ingest_annotations --sheet $K/overlap_ali.csv --out $K/overlap_ali.json
python -m step2_dataset.ingest_annotations --sheet $K/overlap_labmate.csv --out $K/overlap_labmate.json

# optional: LLM labels on the overlap items, for human-vs-LLM agreement (never ground truth)
python -m step2_dataset.llm_label --dataset $D --sheet $K/overlap_ali.csv --out $K/llm_overlap.json \
    --provider anthropic --budget-usd 2

# agreement report + the items to adjudicate
python -m step2_dataset.agreement --a $K/overlap_ali.json --b $K/overlap_labmate.json \
    --llm $K/llm_overlap.json --sheet $K/overlap_ali.csv --disagreements $K/adjudicate.csv

# final labels file: both solo sheets, the agreed overlap items, then the adjudicated ones
python -m step2_dataset.ingest_annotations --sheet $K/solo_ali.csv --out $K/human_labels.json
python -m step2_dataset.ingest_annotations --sheet $K/solo_labmate.csv --out $K/human_labels.json --merge
python -m step2_dataset.ingest_annotations --sheet $K/overlap_ali.csv --out $K/human_labels.json --merge
python -m step2_dataset.ingest_annotations --sheet $K/adjudicate.csv --out $K/human_labels.json \
    --annotator adjudicated --merge

# dataset with the test split pinned to exactly the 400 annotated flows
python -m step2_dataset.build_dataset --prcs data/corpus_run/prcs_all --out data/dataset_g1 \
    --human-labels $K/human_labels.json --test-ids $K/manifest.json
```

Merging `overlap_ali.csv` before the adjudicated sheet means agreed items carry Ali's labels and disagreed items are replaced by the adjudicated ones.
